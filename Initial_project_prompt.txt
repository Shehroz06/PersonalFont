# PersonalFont — Master Development Specification

You are the lead software engineer responsible for building **PersonalFont**, a production-quality handwriting-to-font generator.

## 1. Project Objective

Build a system where a user:

1. Downloads a standardized handwriting template.
2. Prints the template.
3. Writes the required characters by hand.
4. Takes photographs/scans of the completed pages.
5. Uploads 4–6 pages.
6. The system preprocesses and aligns the pages.
7. Extracts each handwritten character.
8. Validates the extracted characters.
9. Normalizes the glyphs.
10. Converts glyphs into vector paths.
11. Generates an installable TTF and OTF font.
12. Generates a font preview.
13. Packages the results into a downloadable ZIP.

The primary goal of V1 is a **reliable deterministic handwriting-to-font pipeline**.

DO NOT implement generative AI or train a new ML model in V1.

---

# 2. Existing Handwriting Engine

The user already has an existing project:

https://github.com/Shehroz06/handwriting-detection-engine

This project contains handwriting analysis functionality and will eventually be integrated into PersonalFont.

Design PersonalFont so that the handwriting engine can be integrated later for:

* handwriting embeddings
* writer/style representation
* handwriting similarity
* few-shot personalized glyph generation

For V1, the font generation pipeline must work independently of the ML model.

Do not duplicate functionality unnecessarily if an existing component from the handwriting engine can later be reused.

Support:

### Uppercase

A-Z

### Lowercase

a-z

### Digits

0-9

### Basic punctuation

.,!?':;"-()[]_

The character set must be configurable.

Do NOT hardcode character coordinates throughout the application.

# 4. Template System

Create a versioned template system.

Example:

templates/
template_v1.pdf
template_v1.json

The JSON must describe:

* page number
* character
* character ID
* bounding box
* expected position
* expected dimensions
* template version

Example conceptual structure:

{
"template_version": "1.0",
"pages": [
{
"page": 1,
"elements": [
{
"character": "A",
"id": "uppercase_A",
"x": 100,
"y": 200,
"width": 150,
"height": 150
}
]
}
]
}

The actual schema may be improved during implementation.

# 5. Image Processing Pipeline

Implement the following modular stages:

INPUT IMAGE
↓
page detection
↓
perspective correction
↓
crop
↓
grayscale conversion
↓
noise removal
↓
thresholding
↓
deskew
↓
template alignment
↓
character extraction

Each stage must be independently testable.

Do not create one huge processing function.

---

# 6. Page Alignment

The system must identify whether the uploaded page corresponds to the expected template.

Support:

* rotation
* perspective distortion
* translation
* scaling
* moderate camera distortion

If alignment confidence is too low, reject the page and return a useful error.

Example:

"Page 2 could not be reliably aligned with template_v1. Please upload a clearer image."

---

# 7. Character Extraction

After alignment, use the template coordinates to extract individual glyph regions.

Each extracted glyph should contain metadata:

* job ID
* page number
* character
* character ID
* source image
* crop coordinates
* extraction confidence

Store temporary results in a job-specific directory.

Example:

jobs/{job_id}/glyphs/A.png

Do not mix files between jobs.

---

# 8. Character Validation

Implement validation for:

* empty glyph
* insufficient foreground pixels
* excessive noise
* multiple disconnected components when inappropriate
* extremely small glyph
* glyph touching crop boundaries
* invalid page
* incorrect template

Return machine-readable validation results.

Example:

{
"character": "A",
"valid": true,
"confidence": 0.97,
"warnings": []
}

If invalid:

{
"character": "B",
"valid": false,
"confidence": 0.31,
"warnings": [
"Insufficient foreground pixels"
]
}

The complete job must NOT fail because one glyph is invalid.

---

# 9. Glyph Normalization

Normalize every valid glyph while preserving its handwriting characteristics.

Operations should include:

* remove unnecessary whitespace
* crop to content
* scale
* center
* baseline alignment
* consistent font metrics
* preserve aspect ratio

Do not distort glyphs unnecessarily.

Create a reusable glyph-normalization module.

---

# 10. Vectorization

Convert normalized glyph images into SVG/vector paths.

Requirements:

* clean contours
* smooth paths
* avoid excessive nodes
* preserve handwriting shape
* transparent background
* correct coordinate system

Keep vectorization separate from font generation.

---

# 11. Font Generation

Generate:

* TTF
* OTF

The font must contain valid Unicode mappings.

Each glyph must have:

* glyph name
* Unicode codepoint
* advance width
* left/right side bearings
* vertical metrics
* baseline alignment

Generate configurable font metadata:

* font family name
* version
* creator
* description

Default family name:

"PersonalFont"

but allow the user to specify a custom name.

# 17. Error Handling

Errors must be explicit and actionable.

Bad:

"Processing failed."

Good:

"Page 3 could not be aligned. The template markers were not detected. Please upload a clearer photograph."

Handle:

* invalid file
* unsupported format
* oversized file
* missing page
* wrong template
* alignment failure
* invalid glyph
* vectorization failure
* font generation failure

---

# 18. Security

Implement:

* upload size limits
* MIME/type validation
* safe filenames
* isolated job directories
* no executable uploads
* configurable cleanup
* no cross-user file access

Never trust user-provided filenames or paths.

# 20. Development Rules

Follow these rules strictly:

1. Do not build everything at once.
2. Work incrementally.
3. After every major module, write tests.
4. Keep modules small and focused.
5. Avoid duplicated image-processing logic.
6. Do not introduce unnecessary dependencies.
7. Prefer deterministic algorithms for V1.
8. Do not train an ML model in V1.
9. Do not implement few-shot generation yet.
10. Do not modify the existing Handwriting Detection Engine unless integration actually requires it.
11. Keep PersonalFont independently runnable.
12. Document important design decisions.
13. Use type hints.
14. Use structured logging.
15. Handle errors explicitly.
16. Never silently discard failed glyphs.
17. Never claim a glyph is valid without validation.
18. Never sacrifice glyph quality merely for processing speed.
